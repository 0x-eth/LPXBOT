# Acceptance Evidence Standard

Each completed work item stores evidence in `artifacts/acceptance/<WORK-ITEM>/` and adds one `manifest.json` validated by `schemas/acceptance-manifest.schema.json`. Evidence directories are created only when a command or review produces real evidence; the 196 feature directories are not pre-created.

## Manifest Rules

- `workItemId`, `phase`, `risk`, and `status` describe the reviewed work item.
- `featureIds` contains unique stable IDs from `docs/FUNCTION_MATRIX.md`. P00 infrastructure work may use an empty array; P01-P13 work must name at least one valid feature ID.
- Every `tests` entry records an allowed Test ID, the exact command, its observed result, and a repository-relative evidence path that exists.
- Every `evidence` entry records an allowed Evidence ID and an existing repository-relative path.
- `assumptions` names unresolved boundaries without upgrading them to verified behavior.
- `completedAt` is an ISO 8601 timestamp only after completion. `commit` is a full Git SHA only when the accepted state is represented by that commit; otherwise it is `null`.
- An `accepted` manifest contains only passing tests. Failed or incomplete work uses the corresponding status and preserves the observed result.

Run `pnpm check:acceptance` to validate every manifest and evidence path.

## Current Inventory

- `P00-03` contains the existing local infrastructure evidence and a manifest referencing only those files.
- `P00-04` contains governance and CI evidence generated by the current work item.
- P00-01 has a frozen artifact manifest and checksums but no work-item acceptance package. This is a recorded evidence gap; no retrospective report is synthesized.
- P00-02 has no standalone work-item acceptance package. Its quality-gate results appear only where they were actually recorded in `P00-03/06-quality-gates.md`; no separate report is synthesized.

## Framework Boundary

Playwright and Foundry are not installed in P00-04. P00-05 will connect real suites to CI after those frameworks and executable tests exist; CI does not include placeholder jobs that always pass.

Gitleaks uses its default rules. Any exception must combine an exact path, a target rule, a narrow matching expression, and a reason in `.gitleaks.toml`; directory-wide artifact exclusions are prohibited.
